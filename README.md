# Турнир на ставках

Сервис на NestJS, PostgreSQL и RabbitMQ. Получает `bet.settled` и `bet.rollback`, начисляет очки с конвертацией в USD и возвращает топ-100 вместе с местом указанного игрока. В комплекте — тестовый продюсер, миграции, Docker Compose и автоматические проверки.

**Правило начисления:** `points = winAmount × курс валюты в USD`. Дробные очки сохраняются. Повторы не начисляют очки повторно, отмена окончательна и работает даже при доставке до расчёта. Все неоднозначности и причины выбора описаны в [DECISIONS.md](DECISIONS.md); правила изменения кода — в [AGENTS.md](AGENTS.md).

## Быстрый запуск в Docker

Нужен Docker с Compose v2. Команды выполняются из корня репозитория.

```sh
docker compose up -d --build --wait
docker compose run --rm producer demo
curl -H "X-Player-Id: demo-alice" http://localhost:3000/leaderboard
```

В PowerShell вместо `curl` используйте `curl.exe`. Обработка очереди асинхронная: если запрос выполнен сразу после публикации, повторите его через секунду. Продюсер дожидается подтверждения RabbitMQ; это не означает, что consumer уже закончил обработку.

Демо публикует расчёты для трёх игроков, дубль, отмену и отмену до расчёта. С конфигурацией по умолчанию ожидаются:

| Место | Игрок | Очки |
| --- | --- | --- |
| 1 | `demo-bob` | `110` |
| 2 | `demo-alice` | `100.25` |
| 3 | `demo-carol` | `0` |

Повтор команды `demo` использует те же идентификаторы ставок и не меняет результат. Таблица предполагает новую БД без других событий и неизменённые демонстрационные курсы.

Адреса: HTTP `http://localhost:3000`, PostgreSQL `localhost:55432`, AMQP `localhost:5673`, [панель RabbitMQ](http://localhost:15673). Демонстрационные логин и пароль: `tournament` / `tournament`. Порты доступны только с локальной машины.

```sh
docker compose logs -f app
docker compose down
```

Обычный `down` сохраняет данные в томах. Команда `docker compose down -v` удаляет данные этого Compose-проекта; используйте её только для намеренного сброса локального демо.

## Локальная разработка

Нужны Node.js 24+ и npm, PostgreSQL 17 и RabbitMQ 4.1. БД и брокер можно поднять в Docker, а приложение запускать на хосте:

```sh
npm ci
cp .env.example .env
docker compose up -d --wait postgres rabbitmq
npm run build
npm start
```

В PowerShell копирование: `Copy-Item .env.example .env`. Если контейнер `app` уже запущен, сначала остановите его через `docker compose stop app`, чтобы освободить HTTP-порт.

В другом терминале:

```sh
npm run produce -- demo
curl -H "X-Player-Id: demo-alice" http://localhost:3000/leaderboard
```

Миграции применяются при запуске сервиса. Их также можно применить отдельно командой `npm run migrate` после сборки. Файлы `.env` и данные контейнеров не входят в Git.

## Контракт событий

Продюсер публикует JSON в durable direct exchange `<QUEUE_PREFIX>.events`. Routing key задаёт тип: `bet.settled` или `bet.rollback`. Тело для обоих типов имеет одну схему:

```json
{
  "betId": "example-bet-001",
  "playerId": "example-player",
  "currency": "EUR",
  "stake": "10.00",
  "winAmount": "25.50",
  "settledAt": "2026-11-06T10:00:00.000Z"
}
```

Сохраните пример в `event.json` и отправьте:

```sh
npm run produce -- bet.settled ./event.json
npm run produce -- bet.rollback ./event.json
```

- `betId` и `playerId`: 1–128 ASCII-символов; первый — буква или цифра, остальные — буквы, цифры, `.`, `_`, `:`, `-`.
- `currency`: три заглавные латинские буквы. Для нового расчёта валюта должна присутствовать в `FX_RATES`.
- `stake`, `winAmount`: неотрицательные десятичные суммы, максимум 12 целых и 8 дробных цифр. Рекомендуются строки; поддерживаются также допустимые конечные JSON-числа. Строки сохраняют точность до разбора JSON.
- `settledAt`: корректная дата и время ISO 8601 с `Z` или явным часовым смещением. Нормализуется в UTC с точностью до миллисекунд; сохраняется в принятом расчёте ставки.
- Все поля обязательны, лишние поля отклоняются. В отмене используются идентификаторы ставки и игрока; сумма снимается из сохранённого расчёта.
- Размер тела сообщения — не более 16 КиБ.

Для нового `betId` отправляется один расчёт. Повтор того же нормализованного расчёта безопасен. Изменение ранее принятого расчёта с тем же `betId` считается конфликтом. После отмены переоткрыть ставку нельзя.

## HTTP API

### `GET /leaderboard`

Обязательный заголовок: `X-Player-Id`. Пример результата после демо:

```json
{
  "top": [
    { "playerId": "demo-bob", "points": "110", "position": 1 },
    { "playerId": "demo-alice", "points": "100.25", "position": 2 },
    { "playerId": "demo-carol", "points": "0", "position": 3 }
  ],
  "player": { "playerId": "demo-alice", "points": "100.25", "position": 2 }
}
```

`top` содержит максимум 100 игроков. `player` содержит место во всём турнире, в том числе за пределами топ-100. Для неизвестного игрока возвращаются `points: "0"` и `position: null`. Пустая БД возвращает пустой `top`. Отсутствующий или некорректный заголовок — HTTP 400.

При равных очках порядок определяется `playerId` по возрастанию (`C` collation); места последовательные. Игроки с нулевым счётом после обработанной ставки остаются участниками. `points` — десятичная строка, не JSON-число. Заголовок идентифицирует запрос и не реализует аутентификацию.

### `GET /health`

Проверяет готовность приложения, PostgreSQL и consumer RabbitMQ. Используется healthcheck контейнера; недоступность зависимости означает HTTP 503.

## Настройки

| Переменная | Значение по умолчанию / назначение |
| --- | --- |
| `DATABASE_URL` | `postgresql://tournament:tournament@localhost:55432/tournament` |
| `RABBITMQ_URL` | `amqp://tournament:tournament@localhost:5673` |
| `PORT` | `3000` |
| `FX_RATES` | `{"USD":"1","EUR":"1.10","GBP":"1.25"}`; USD за единицу валюты |
| `QUEUE_PREFIX` | `tournament`; префикс exchange и очередей |
| `PREFETCH` | `16`; число неподтверждённых сообщений consumer |
| `MAX_RETRIES` | `5`; число повторов после первой попытки |
| `RETRY_DELAY_MS` | `1000`; задержка повторной доставки |

Это демонстрационные курсы. Курс новой ставки фиксируется в БД; его изменение не пересчитывает старые результаты. Некорректная конфигурация останавливает запуск. В контейнерах адреса БД и брокера указывают на имена сервисов Compose.

## Доставка, повторные попытки и DLQ

```text
producer → <prefix>.events → <prefix>.bets → транзакция PostgreSQL → ACK
                                  │
                                  ├─ временная ошибка → <prefix>.retry → повтор
                                  └─ постоянная ошибка / лимит попыток → <prefix>.dead
```

Состояние ставки и итог игрока меняются одной транзакцией. Блокировка строки ставки защищает от конкурентных дублей и отмен; атомарное изменение агрегата защищает разные ставки одного игрока. ACK отправляется после коммита. Доставка повторяется при сбоях, поэтому идемпотентность обеспечивается в БД.

Retry и DLQ сохраняют исходное тело. Публикация в них подтверждается брокером до ACK исходного сообщения. Служебные заголовки: `x-original-routing-key` сохраняет тип события, `x-retry-count` — число повторов, `x-error-code` — категорию ошибки DLQ без содержимого события. Невалидные события и конфликты не повторяются автоматически. В RabbitMQ Management можно проверить `<QUEUE_PREFIX>.dead`, исправить причину и вручную повторно отправить исходное тело в `<QUEUE_PREFIX>.events` с нужным routing key без служебных заголовков повторов. Не удаляйте DLQ до разбора причин.

Очереди quorum, но локальный Compose использует один узел RabbitMQ: отказоустойчивый кластер этим не имитируется. Изменение аргументов уже созданных очередей может потребовать нового `QUEUE_PREFIX` или осознанного пересоздания локальных очередей.

## Проверки

```sh
npm ci
npm run check
npm test
docker compose up -d --wait postgres rabbitmq
npm run test:integration
```

Модульные тесты проверяют суммы, контракт и конфигурацию. Интеграционные тесты используют реальные PostgreSQL и RabbitMQ, отдельную схему БД и уникальный префикс очередей; после себя удаляют только свои ресурсы. Запускайте их на локальных тестовых зависимостях. Проверяются повторы, конкурентные события, отмены, точность счёта, граница топ-100 и HTTP-контракт.

## Структура

- `src/bets/` — валидация событий, расчёт очков и транзакционная обработка.
- `src/messaging/` — topology RabbitMQ и consumer.
- `src/` — конфигурация, подключение БД, лидерборд и приложение NestJS.
- `scripts/` — миграции и тестовый продюсер.
- `test/` — модульные и интеграционные проверки.

Репозиторий предназначен для проверки задания в локальном окружении. Ограничения бизнес-контракта и дальнейшие эксплуатационные задачи перечислены в [DECISIONS.md](DECISIONS.md).
